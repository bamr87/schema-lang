# Product Requirements Document (PRD): schema-lang

> A Rust DSL and compiler for gitorio/SCHEMA blueprints: parse, type-check and emit SCHEMA.md contracts.

Open work is tracked in [GitHub Issues](https://github.com/bamr87/schema-lang/issues) and as `status: planned` entries in [features/features.yml](features/features.yml).

## 1. Overview

Turn the fleet's structural contracts into a real language: a lexer, parser, checker and code generator for SCHEMA blueprints.

| Version | Date | Notes |
| --- | --- | --- |
| 0.1 | 2026-10-28 | Initial requirements and phased roadmap (repo foundation). |

## 2. Goals

- Lexer and parser for a small blueprint DSL
- Semantic checks with good error messages
- Emit SCHEMA.md / gitorio blueprint files

Non-goals (near term): production hosting, paid services, anything outside the roadmap below without a PRD change.

## 3. Users

- The maintainer, learning compiler front ends (lexing, parsing, asts), type checking and diagnostics by building.
- Fleet agents (hub evolution loop, backlog fan-out, `evolve` lane) that grow the repo one reviewed PR at a time.
- Fleet tie-in: Compiles blueprints for bamr87/gitorio and bamr87/SCHEMA; validates against the hub's schema_lint.py rules.

## 4. Requirements

Phases are the build order: an agent picks the earliest unserved requirement first.

### 4.1 Phase 1 — Foundation

- FR1: Lexer tokenizing identifiers, strings and punctuation, with tests
- FR2: CLI that reads a .schema file and prints tokens

### 4.2 Phase 2 — Core

- FR3: Recursive-descent parser producing an AST
- FR4: Semantic checks with span-based diagnostics

### 4.3 Phase 3 — Fleet integration

- FR5: Emit SCHEMA.md contracts and gitorio blueprints
- FR6: Language server (LSP) for editors

### 4.4 Non-functional

- NFR1: CI (`.github/workflows/ci.yml`, the fleet standard gate) passes on every PR.
- NFR2: No secrets or credentials are committed; configuration comes from environment variables.
- NFR3: Autonomous lanes are off by default, open pull requests only, and never merge.
